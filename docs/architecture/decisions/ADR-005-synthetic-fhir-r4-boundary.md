# ADR-005 — Synthetic FHIR R4 Data and Read-Broker Boundary

**Status:** Accepted; local Synthea/HAPI slice verified  
**Date:** 2026-08-11  
**Owners:** Data Steward, Interoperability Lead, Privacy Officer, and AI Security Lead  
**Related:** REQ-DAT-001/003/004, REQ-IAM-005, REQ-RAG-002/006, CTL-DAT-001, CTL-RAG-002

## Context

The M01 patient service uses typed in-memory records. M04 must demonstrate healthcare-shaped data,
security labels, consent, provenance, delegated authorization, field minimization, and safe FHIR
failure without introducing real PHI or letting raw FHIR resources enter model context.

## Decision

The repository will use FHIR R4 (4.0.1) synthetic resources. The source dataset will be generated by
a pinned Synthea workflow and stored as a versioned, checksummed Bundle with a public-safe manifest.
No production export, real patient seed, or user-supplied clinical record may enter the generator or
repository. The implemented pipeline pins Synthea v4.0.0 and a Java 17 image by digest, runs the
generator without network access, proves two raw runs byte-identical, replaces source identifiers
and direct-contact fields, and emits a checksummed minimum-view Bundle and public-safe manifest.
Hand-authored in-memory fixtures remain separate contract fixtures and are not called Synthea output.

HAPI FHIR JPA starter v8.10.0-3 is the local integration target behind the provider-neutral gateway,
pinned to image digest `sha256:55213612779ab3eeec919226b7bad378f0061ade823393a61d7dd46dd5087a3d`.
The disposable lab binds to loopback, runs non-root/read-only with dropped capabilities, uses no
persistent database, and contains synthetic data only. The fast in-process adapter and HAPI HTTP
adapter pass the same broker contract. The upstream starter has no enterprise authentication or
enterprise logging and is not an EHR or production component.

All FHIR access passes through a read broker that:

1. accepts typed authenticated end-user, purpose, resource, operation, facility, and patient
   context—not a model-generated query or reusable credential;
2. obtains or receives an audience-bound minimum-scope downstream token only through the trusted
   identity broker; incoming token passthrough is forbidden;
3. reads only minimum Patient security context plus active Consent, authorizes before the full read,
   and rechecks patient/facility/security/source/Consent context before releasing a view;
4. converts approved resources into an explicit minimum `PatientSummary`; raw Bundle, narrative,
   unknown extensions, and unrelated fields never enter model context;
5. treats FHIR narrative and extensions as untrusted data; and
6. fails closed and emits a minimized AuditEvent-shaped record when identity, policy, consent,
   labels, provenance, schema, or the FHIR dependency is unavailable or inconsistent.

Part 2-style fixtures use synthetic security/consent labels to exercise stricter authorization. They
are educational analogs, not a legal encoding decision. The exact terminology/profile and legal
interpretation require Privacy, Legal, Records, and interoperability validation before real use.

## Required provenance manifest

The dataset manifest records generator/tool version, configuration, seed, generation time, FHIR
version, resource counts, checksums, synthetic-use notice, license/source, transformation steps,
labeling method, validation results, and reviewer role. A scan must confirm no known real source or
credential was used. Dataset changes trigger the same risk/evaluation gate as a corpus change.

## Verified local result

- Canonical dataset `NS-SYN-FHIR-R4-001` contains 3 Organizations, 3 Patients, 3 active permit
  Consents, and 3 Provenance resources.
- Required Restricted and SYNTHETIC labels and `meta.source` survive HAPI persistence/readback.
- Permit is required; deny, missing/ambiguous Consent, and post-authorization Consent change fail
  closed without releasing the Patient view.
- HAPI reports FHIR 4.0.1 / HAPI 8.10.0; the shared broker integration contract passes.
- This is bounded interoperability evidence, not profile validation, SMART conformance, legal
  sufficiency, or production readiness.

## Consequences

- The read broker, not the model, owns FHIR query construction and minimum-view projection.
- SMART-style scopes bound delegation but do not replace Northstar contextual authorization.
- HAPI availability, timeout, malformed Bundle, patient mismatch, label loss, consent revocation,
  and token/policy failure require negative contract tests.
- Durable storage, retention, deletion, backup, and provider lifecycle decisions remain `BLK-001`.
